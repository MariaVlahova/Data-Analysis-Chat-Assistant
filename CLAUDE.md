# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this is

A CLI chat agent for non-technical retail executives. It answers sales questions on BigQuery (`bigquery-public-data.thelook_ecommerce`: `orders`, `order_items`, `products`, `users`), explains causes and writes reports with action items. Each user is a brand manager and sees only their brands. The CEO sees all brands. PII never appears in an answer.

It is a 6 to 12 hour take-home prototype for the client OpsFleet. The assessment weighs system design, the technical explanation and an elegant prototype.

## Architecture in one screen

A LangGraph state graph with fixed steps and two bounded loops (SQL repair, replan):
`Input Guard` → `Context Assembly` → `Planner` (why and report turns only) → `SQL loop` (SQL Guard → BigQuery dry-run → execute → Result Guard) → `Evidence Check` → `Composer` → numeric check → `Output Guard`.
Delete and save requests skip the SQL path: `Input Guard` → `Tool Router` → `HITL Gate` (LangGraph `interrupt`) → tool.
Gemini calls go through one gateway (rate limiter, retry with jitter, circuit breaker, Flash to Flash-Lite fallback, per-turn call budget).

Planned layout: `src/{access,cli,storage,data_access,observability,llm,guards,agent,tools,reports,golden,localdata}`, plus `config.yaml`, `config.local.yaml`, `users.yaml`, `users.local.yaml`, `schema_allowlist.yaml`, `glossary.yaml`, `golden/seed/`, `eval/`, `data/` (runtime, git-ignored). Plan 01 has the full tree.

Prototype scope: Safety and PII, High-Stakes Oversight (delete saved reports), Resilience, Observability. **Design-only:** Golden Bucket retrieval (an optional seeded slice exists), system learning loop, quality assurance pipeline. Never describe a design-only item as working. **Out of scope (owner decision, 2026-10-22):** the memory agent and any learned user profile; persona management (editor UI, registry, versions, approval, rollback, per-user style, persona switching). Do not plan, design or build them. The persona is one static file, `personas/default.yaml`.

## Rules for working here

- **Code enforces security, the model only suggests.** Every model output is checked by code. A guard violation is never retried.
- **Real customer IDs, report IDs and raw result rows never reach the model, graph state, traces or logs.** The Result Guard replaces `users.id` with a fixed fake ID per session. Raw DataFrames stay local to the node that runs the query. Keep the pseudonymizer and API clients out of graph state and LangGraph config.
- **All agent queries go through `SafeQueryRunner`** (plan 03), after the SQL Guard. The old `BigQueryRunner.execute_query` no longer exists, and `SafeQueryRunner` keeps its client private; `tests/test_no_direct_execute.py` fails if a file outside `data_access/` mentions `execute_query` or imports a BigQuery client. Our own fixed SQL uses `SystemQuery`, never model-written SQL; the same test keeps the name inside `data_access/`. `run()` refuses any query type that is not in `safe_runner.ACCEPTED_QUERY_TYPES` (`SystemQuery` and `GuardedQuery`), so a look-alike object with `.sql` and `.params` cannot run. Only `SQLGuard.check` makes a `GuardedQuery` (`GuardedQuery.issue`), every field is sealed, and the runner refuses one that was changed or made elsewhere; `tests/test_guarded_query_origin.py` fails if anything else calls `issue`. Keep a `GuardedQuery` in the process that made it.
- **Model-written SQL goes through `SQLGuard.check` before anything else** (plan 05). The text that runs is regenerated from the rewritten parse tree, never the model's text. A `GUARD_VIOLATION` is never retried; `SQL_SYNTAX` and `SQL_UNKNOWN_COLUMN` may be repaired. A column that is not in `schema_allowlist.yaml` does not exist for the agent. `src/guards/` must not import the BigQuery library (`SafeQueryRunner` turns `ArrayParam` into BigQuery's parameter).
- **All model calls go through `LLMGateway.generate()`** (plan 04) with the turn's `TurnBudget`, for Gemini and for the local model alike (`tests/test_openai_compat.py` fails if a file outside `src/llm/` mentions `chat/completions`). It owns the retries (the SDK's are off), so every outbound attempt is one charged call. `tests/test_no_direct_gemini.py` fails if a file outside `src/llm/` imports the Google SDK or calls `generate_content`. A provider error's text is never kept: the gateway's details are `HTTP <code> <status word> from <model>` only.
- **Query rows go through `ResultGuard.apply` in the node that runs the query, and the final answer through `OutputGuard.check` before anything is printed** (plan 06). Only a `GuardedResult` leaves the node. Keep the `SessionPseudonymizer` in a closure: `copy` and `pickle` refuse it on purpose. A guard that fails raises `RESULT_GUARD_FAILED` or `OUTPUT_BLOCKED` and returns nothing; never catch it to show "what we have". The answer the Output Guard held back is never stored in a span, a log or a state field, not even masked: `/trace` shows users their own turns. Render `GuardedResult.notices` into every answer. `pii.scan(text)` is the short list for traces and logs; `extended=True` adds address, coordinates and postal code for guards.
- **Text the Output Guard has not passed lives in `TurnRuntime.scratch`, never in graph state** (plan 07). Hold it with `runtime.hold(KEY, ...)`; the keys are `deps.UNCHECKED_KEYS`, and the error boundary drops them all. State is checkpointed. `answer`, `title` and `notices` are written by `output_guard` after the check passes. Report IDs, a `GuardedQuery`, DataFrames and the pseudonymizer are never in state either. `tests/test_graph_state.py` plants canaries and searches every checkpoint, trace and log.
- **Every turn starts from `fresh_turn_input`** (`src/agent/state.py`). State carries over between the turns of a conversation (the checkpoint thread is the conversation), so every per-turn field is reset. Only `history`, `last_answer` and `shown_labels` (the numbers of the `Customer #NNNNN` labels the user was shown, so a new process still refuses them as IDs) carry on purpose. A node returns the whole value of a key it changes; the state has no reducers.
- **The graph never names a tool.** The Tool Router asks the registry by intent. A gated tool (destructive or external-send) names a finder. `prepare_action` has no side effect. The confirmation holds a hash of the ID set, and the IDs stay in the node that found them. `hitl_gate` is only the `interrupt()`. Only the resume value, the line the user typed, confirms.
- **A `Customer #NNNNN` label is never an ID.** Its digits are a random number in the range of real customer IDs. A query that holds the number of a label the session has shown is refused (`SESSION_LABEL`), and so is a question that names a label (plan 06, plan 07).
- **Mask before writing.** Spans, logs and metrics go through `src/pii.py`, and so does what the user types before it enters graph state (`AgentRuntime.run`), because a checkpoint is kept on disk for 90 days. Identity in traces, metrics, audit rows and BigQuery labels is a user hash, not the login name.
- **Emit spans and counters through `src.observability`,** with the span names in plan 02. A model call or a query is both a span and a `turn_metrics()` call. Log through `logging.getLogger(__name__)` under `src`, never the root logger, or the line skips the masking filter. Never log or store the text of a caught exception (a BigQuery error can quote SQL literals that no pattern masks): use `crash_summary(exc)`. Never put a DataFrame or rows in a span attribute. An `AgentError`'s own `detail` is the one exception text allowed: our code wrote it, it is short and it is masked when the error is built. One deliberate case: `SQL_SYNTAX` and `SQL_UNKNOWN_COLUMN` details carry BigQuery's normalized message with quoted tokens blanked, because the repair step needs the position and the unknown name (`errors_map.py`).
- **Empty brand list means no access, never "all brands".** The CEO has an explicit all-brands flag.
- **Only the user's typed reply confirms a destructive action.** Never text from a model, a question or a stored report.
- **Saved reports go through `ReportStore`** (plan 08). The owner is an argument of every query, never something the model wrote. An effect and its audit row are one transaction, so no effect happens without a record. `audit_log` is append-only and holds user hashes, counts, keyed hashes and trace IDs, never text, titles or report IDs. A repeat with the same idempotency key returns the first result and writes no second row. `tests/test_audit.py` and `tests/test_idempotency.py` fail if one of these breaks.
- **Do not guess brand or column names.** Read them from the live schema and brand list (plan 03). The brands of `users.local.yaml` and of `g-009`, `g-010` are the sample data's own, made up by `src/localdata/generate.py`; they say nothing about the real dataset.
- **The Golden Bucket filters before it scores, and never puts trio text in a trace** (plan 10). A trio is eligible when it is `approved` and brand-agnostic, or every brand of it is the user's, or the user sees all brands (S5). A brand name in a trio's text that is not among its own brands fails `golden validate`. The `golden.retrieve` span holds IDs and scores, never text. Retrieved text goes into prompts inside `<untrusted_data source="golden_trio">`. A trio is an example, never an instruction.
- **Reference queries bypass the guards on purpose, and only the scenario runner may use them.** `ReferenceQueries` (`data_access/reference.py`) reads the data with no brand filter and no allow-list to learn the right answer of a scenario. It keeps the runner's dry run, byte cap and SELECT-only check. Nothing outside `src/scenarios` and `src/data_access` may import it (`tests/test_reference_queries.py`).
- **`eval/` is test tooling and goes through the same doors as the app** (plan 09). Nothing in `src/` imports it (`tests/test_eval_boundaries.py`). Its reference SQL runs through `SQLGuard.check` and `SafeQueryRunner` as the same user, never through `ReferenceQueries` (the scenario runner's bypass) or a client. A check that could not be made is "not applicable" and a check the data gave nothing to act on is "not exercised": neither is a pass, and a hard gate that nothing measured is reported as unmeasured. An answer with personal data is withheld from the run's files. The `model:` scripts of `attacks.yaml` are for the offline run only. A baseline belongs to one environment, data and model, and is never written from a run that leaked or skipped a case.
- **The trajectory checks hold the code to a design written by hand** (plan 09, `eval/trajectory.py`). `NEXT` (what may follow what), `MAKERS` (which node makes which per-turn field of the state) and the other tables are typed out on purpose: a table read off the graph would agree with any bug in it. `tests/test_trajectory_contract.py` fails when the compiled graph differs from `NEXT`, when the code opens a span the vocabulary does not know, or when `fresh_turn_input` gains a field no rule covers, so a change to the graph or the state means reading that file. The checks read the spans and `TurnEvidence.state` (the checkpoint after the turn, from `AgentRuntime.state_of`, without result rows); the state stays in memory and no run file holds it. A rule that fails on a legitimate path is a bug in the rule: replay real traces before widening one. A check that has only ever passed has not been shown to look, so each rule has a test that breaks the app in one place (`tests/test_trajectory_offline.py`).
- **The judge is advisory, goes through the gateway and is never the model that answered** (plan 09). `src/evaluation/judging.py` (shared by `eval/judging.py` and the chat's `/eval`) calls `LLMGateway.generate(Step.JUDGE, ...)` only (the same no-SDK tests apply to `eval/` and `src/evaluation/`), and a judge score never changes an exit code, a baseline or a hard gate. `judge_run` refuses a judge whose model is the run's (decision 3.13) unless `allow_self_judge`, and then marks every file `independent: false`. Which rubric can apply to a turn is decided in code (`APPLICABILITY`; a row added to `rubrics.xlsx` needs a rule, `tests/test_eval_judge.py`), a failed judge call is N/A and never a pass, a turn the run withheld for personal data is judged by nothing, and the judge never sees a result row.
- **`/eval` is the only way the judge starts in the chat, and the daily budget is counted in tokens** (plan 09, NFR8). A chat turn makes no judge call (`tests/test_live_eval.py` fails if one does). Only `src/evaluation/` imports `evalkit` (`tests/test_eval_boundaries.py`), `src/evaluation/live.py` gives the judge a gateway of its own with a cost hook (every attempt, a failed one too, is counted; chaos is not injected into it), and the judge sees only what `evidence.py` hands it (no result row, no turn with personal data). A judge call that fails is "no verdict", never a pass, and such a turn is judged again by the next `/eval`. `evaluations.jsonl` and `token_usage` hold counts, scores, user hashes and trace IDs, never text. The daily cap is checked before a turn starts, so the turn that crosses it still finishes; `/budget clear` adds a `budget_clears` row and an audit row (`budget_cleared`) in one transaction and deletes no usage row.
- **Sample data is a development aid.** `bigquery.backend: local` changes only the engine behind `client.query` and `client.get_table`; `SafeQueryRunner` and every guard run unchanged. It shows what the guarded SQL means on real tables, not that BigQuery accepts it, so it never stands in for `pytest -m live` or the live steps of plans 03 and 05. Keep `duckdb` imported lazily and `src/localdata/` free of the BigQuery library (`tests/test_no_direct_execute.py`). Say `LOCAL SAMPLE DATA` wherever a local run could pass for a live one (the banner and `doctor` do).
- **Be sparing with live Gemini calls.** The free tier is rate-limited. Use the scripted fake gateway and fake BigQuery runner in tests.
